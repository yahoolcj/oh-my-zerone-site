# 0002 to-test 改为 TDD 红绿灯验收测试

`to-test` 原本是事后问询式验收（不跑脚本、不改代码、不落盘报告），功能验收仍要靠人工点击；现改为 ATDD 风格的红绿灯双阶段：**red** 在 `to-coding` 之前按 issue 验收标准生成清单并跑出失败证据，**green** 在编码之后重放清单产出绿灯，全绿即视为验收通过并自动勾选 issue 验收项与对应 PRD TODOQ。清单嵌入 issue 文档，执行层用「浏览器能力阶梯 + 适配器协议」，证据落 `.TEST/<PRD版本>/` 且不入库；明确不做单元测试、不设编码前硬门禁。执行器阶梯为五级：项目内 Playwright → 浏览器类 MCP → 系统 Chromium headless CLI（Edge / Chrome）→ orca-cli / computer-use → 人工步骤。

## 已考虑的备选方案

- **事后回放红**（stash / checkout 基线代码制造红）：不改工作流顺序，但红灯是回放产物，无法证明用例在真实时序下有效 —— 否决，采用编码前真红。
- **Playwright 唯一标准**：红绿证据最硬、可入 CI，但本机与 Claude Code / Cursor / DSH 多 harness 下均无 Playwright，强制新增依赖违反「不引入新依赖来替代仓库已有能力」 —— 否决，改为能力阶梯 + 适配器协议。
- **保留单元测试**（项目 runner 或 Node 22 内置 `node --test` 零依赖）：用户明确选择不做单元测试，测试面收敛为浏览器全流程行为 —— 否决。
- **清单落 `.TEST/<版本>/` 独立目录**：跨会话恢复更稳，但清单与验收标准分离、review 时需多处对账 —— 否决，改为嵌入 issue 文档；清单仅承载过程状态，不作为独立数据资产。
- **保留「未获用户验收禁止打勾」门禁**：与「TDD 绿灯即验收」目标冲突；用户明确授权改红线 —— 否决，改为全绿自动打勾。
- **跨 issue 主干流程放 PRD 附录**：层级更清晰，但需放宽「to-test 不写 PRD 正文」约束 —— 否决，改为挂到端到端验收 issue。

## 后果

- `workflow.md` step5 与 `to-coding` 的勾选规则必须同步改写：to-coding 不再承担验收勾选权，由 to-test 在全绿后自动勾选。
- 无浏览器自动化能力的环境降级为黄灯（附可照做的人工步骤），禁止冒充绿灯；黄灯项需人工确认后才可转绿。
- 跨 issue 主干流程依赖「端到端验收 issue」存在；缺失时 to-test 只报缺口，不自动创建 issue（由 `/to-issues` 补齐）。
- `.TEST/` 证据目录必须加入 `.gitignore`，避免截图/录屏进入仓库。
- 绿灯自动打勾意味着旧红线「未获用户验收禁止打勾」作废，属于用户显式授权的规则变更，需在 AGENTS/omz-governance 同步措辞。
