# 2.4.0

## to-test 红绿灯验收测试（TDD 驱动）

> 类型：优化升级

### 概述

把 `to-test` 从「事后问询式验收回收」升级为 TDD 驱动的红绿灯验收测试：`red` 阶段在编码前按 issue 验收标准生成红绿灯清单并跑出失败证据（红证据），`green` 阶段在编码后重放清单，全绿即自动勾选 issue 验收项与对应 PRD TODOQ；功能测试由浏览器自动化能力阶梯驱动，不再依赖人工点击页面；明确不做单元测试、不设编码前硬门禁。清单嵌入 issue 文档，证据本地落盘不入库，测试回收报告仍在对话输出。

设计决策与备选方案见 `docs/adr/0002-to-test改为红绿灯验收测试.md`；术语见 `CONTEXT.md` 测试术语章节（红绿灯清单、红证据、端到端验收 issue）。

### 数据模型 Schema

#### 红绿灯清单（issue 文档固定章节）
| 字段 | 控件 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|------|--------|------|
| id | - | string | 是 | - | 用例编号，`RG-01` 起顺序递增 |
| criterion | - | string | 是 | - | 关联的 issue 验收标准原文 |
| todo | - | string | 否 | - | 关联的 PRD 功能清单条目 |
| flow | - | string | 否 | - | 所属跨 issue 主干流程名（仅端到端验收 issue 使用） |
| precondition | - | string | 否 | - | 前置条件（登录态、测试数据、初始路由） |
| steps | - | string[] | 是 | - | 可重放的操作意图序列（人可读，允许按文案/角色定位） |
| assert | - | string[] | 是 | - | 断言集合（可见文案、元素状态、URL、接口结果） |
| executor | - | string | 是 | - | 当次执行器：playwright / mcp / orca-cli / computer-use / manual |
| red_evidence | - | object | 是 | - | 红证据：执行器、时间、日志与截图路径、失败摘要；缺失即用例作废 |
| light | - | enum | 是 | 黄 | 当前灯：绿 / 黄 / 红 |
| yellow_reason | - | enum | 否 | - | 黄灯原因：待人工确认 / 无自动化能力 / 阻塞 |
| green_evidence | - | object | 否 | - | 绿证据：执行器、时间、截图路径 |

#### 红绿灯清单 YAML 摘要（清单章节头部）
| 字段 | 控件 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|------|--------|------|
| prd_version | - | string | 是 | - | PRD 版本号，如 `2.4.0` |
| issue | - | string | 是 | - | issue 文件名 |
| phase | - | enum | 是 | red | 当前阶段：red / green |
| cases | - | array | 是 | - | 用例摘要数组，字段与用例卡对齐（不含 steps 正文） |
| generated_at | - | string | 是 | - | 生成时间（ISO 8601） |

#### 证据目录 `.TEST/<PRD版本>/<issue>-<时间戳>/`
| 路径 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `screenshots/*.png` | 文件 | 否 | 逐步骤截图，命名 `<RG-ID>-<step>.png` |
| `logs/run-<phase>.log` | 文件 | 是 | 执行器原始输出与断言结果 |
| `notes.md` | 文件 | 否 | 人工确认步骤与用户确认记录 |
| `.gitignore` 规则 | 配置 | 是 | 根 `.gitignore` 忽略 `.TEST/` |

#### 灯状态枚举
| 值 | 含义 | 是否可自动打勾 |
|----|------|----------------|
| 绿 | 用例重放通过且断言全部满足 | 是（全绿时） |
| 黄 | 待人工确认 / 无自动化能力 / 阻塞 | 否 |
| 红 | 用例失败或修复后仍失败 | 否 |
| 作废 | 缺少红证据，不参与判定 | 否 |

### 页面交互

- 命令入口：`/to-test red`（生成清单 + 跑红）与 `/to-test green`（重放清单 + 判定灯）；无参数调用时先询问阶段，不做猜测。
- 红阶段输出：红绿灯清单落盘位置、用例数与覆盖缺口、红证据摘要、下一步提示（进入 `/to-coding`）。
- 绿阶段输出：灯统计（绿/黄/红）、自动勾选结果（issue 验收项与 PRD TODOQ）、黄灯人工步骤、红项返工单、下一步提示（全绿 → `/to-review`；有红 → `/to-coding` 返工；有黄 → 人工确认）。
- 不修改产品代码；不创建 PRD / issue；不提交 commit；测试回收报告只在对话输出，不落盘。

### 扩展性要求

- 执行器适配器协议可扩展：未来新增 CLI 适配器（命令行流程断言）时不改清单主体结构，只扩展 `executor` 枚举与执行分支。
- 灯状态与用例 Schema 预留版本字段，未来若恢复单元测试可作为新用例类型接入。
- 浏览器能力阶梯顺序可配置，便于接入新的浏览器 MCP。
- 记忆引导保留，触发条件改为「全绿且无黄」。

### 用户故事

1. 开发前用户运行 `/to-test red`，在 issue 文档得到红绿灯清单与失败证据，确认覆盖后直接进入 `/to-coding` 编码。
2. 编码完成后用户运行 `/to-test green`，全绿时自动勾选 issue 验收项与 PRD TODOQ，并提示进入 `/to-review`。
3. 绿阶段存在红灯时，to-test 输出返工单交给 `/to-coding` 修复，修复后重跑直到全绿（建议 3 轮后转人工）。
4. 环境无浏览器自动化能力时，相关用例标黄并附可照做的人工步骤，用户照做确认后才可转绿，系统不得冒充通过。
5. 非 Web 项目运行 to-test 时，技能说明不适用并退化为原问询式验收回收。
6. 跨 issue 的主干流程在端到端验收 issue 中一次跑通，作为整份 PRD 的收口绿灯。
